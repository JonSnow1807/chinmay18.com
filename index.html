Distributed systems · live at mustard.watch

Mustard Watch Party

Multi-instance-capable video synchronization with a model-checked control protocol.

Clients connect over WebSockets, estimate a clock offset from the socket acknowledgement (NTP-style) and correct drift with predictive rate control; room state lives in Redis behind atomic Lua scripts. The 48 ms P95 is a specific claim: steady-state, player-reported drift across three Chrome clients at roughly 300 ms simulated RTT over a 240-second run. A separate audio-output measurement showed the player API understates true skew by about 45 ms at P95, so the number is quoted as player-reported, never as physical sync.

TLA+/TLC model checking exposed a stale-epoch bug after store resets, which led to ordered epochs; idempotency keys plus atomic updates give at-most-once application of control commands under duplication and reordering. The multi-instance path is proven in a three-instance lab and nightly CI; production currently runs one backend instance. Go and Rust relays were built as conformance studies, not the production backend: at 10,000 local connections the Rust relay used 14.5 KB per connection against 40 KB for Go, while the tail-latency comparison was inconclusive.

GPU kernels · PyTorch custom ops

Fused LayerNorm / RMSNorm CUDA operators

Residual-add fusion, FP8 outputs and a deterministic backward, with no graph breaks under torch.compile.

The eager composite runs residual-add, normalization and an FP8 cast as three kernels with HBM round-trips; the fused version does all three in one. Parameter gradients use fixed-order reductions instead of atomic accumulation, which is where the determinism comes from. The modules register through torch.library.custom_op, so compiled graphs stay whole.

For dynamic RMSNorm-to-FP8 in fp16 on an A100 I measured 4.9–7.2× over the eager composite and 1.04–1.76× over the compiled composite across six shapes. Those are kernel-time comparisons, not end-to-end model speedups, and the compiled-composite win does not transfer to the H100, where the repository documents 0.70–1.20× and makes no claim. The non-FP8 fused-add ops sit at parity with compiled PyTorch.

Performance tooling · on PyPI as pytorch-autotune 2.0

PyTorch AutoTune

Measure the training configuration instead of guessing it.

The tuner benchmarks precision, compile mode, memory format and fused-optimizer combinations on the target model and batch, under a time budget. A winner has to beat the incumbent by more than 3 %, the search never returns a configuration slower than the baseline, and the report records every trial together with compilation cost and estimated break-even time.

Against PyTorch-default fp32 eager on an A100 the tuned stack reached 2.71× on ResNet-50, 3.84× on ResNet-18 and 6.65× on a six-layer Transformer; against plain torch.compile it was 2.0–6.1×. The baseline matters: with TF32 matmuls enabled the Transformer gain is 2.55×, not 6.65×. Rebuilding the winners in a fresh training loop reproduced the committed numbers within 1.5 %. Earlier versions advertised a 4.06× T4 result and an energy figure; both were retracted in the changelog because nothing committed supported them.
